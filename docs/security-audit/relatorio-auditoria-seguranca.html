Sessão e recuperação de senha robustas
Token de sessão hasheado (sha256) em banco (authService.ts:116); membership revalidado a cada request (:123-131); troca de senha revoga todas as sessões (auth.ts:107-118); recovery com token 256-bit hasheado, single-use, 1h de TTL, rate-limit e resposta que não vaza existência de conta (recoveryService.ts:27-67); rate-limit em login (10/15min), invitation-accept, password-reset e aprovações públicas (lib/rateLimit.ts).

Nenhum dangerouslySetInnerHTML/eval/new Function no src (grep). Links de chat aceitam só http/https (formatMessageText.tsx:40-42,62); DocumentBubble restringe href a http/https//api (DocumentBubble.tsx:27-33); avatares/logos vão apenas para <img src> (esquemas javascript:/data: são inertes em img).

Pontos fracos (riscos centrais)

1. Cadeia de confiança de mídia: a validação de URL aceita qualquer esquema e o frontend renderiza em href clicável (A1) — única rota de XSS encontrada.
2. Higiene de segredos entre repositórios: a credencial admin real vazou para o repo de marketing/captura (A2) — o repo do Looply em si está limpo.
3. Defesa de configuração: startup não rejeita placeholders de segredo (A4); e-mail usa input sem escape (A3).

--- ISSUE 1 ---
**[Segurança] XSS armazenado via mediaUrl com scheme javascript:**

Labels: `security, alta`

## Descrição do problema
Membro autenticado do workspace cria uma versão de conteúdo (POST /api/contents/:id/versions) com mediaUrl="javascript:payload". O validador zod .url() aceita qualquer esquema com dois-pontos (testado: javascript: e data: passam). Outro usuário da mesma equipe abre o conteúdo e clica em "Ver mídia" — o anchor executa o scheme javascript: no contexto da aplicação. Não há biblioteca de sanitização no projeto. Condições: atacante precisa ser membro convidado + vítima clica; reflete-se em roubo de cookie de sessão (httpOnly mitiga exfiltração direta, mas o script roda como a vítima na origem).

## Evidência
`backend/src/lib/validation.ts:18,25 · frontend/src/features/ContentDetail.tsx:889`

```
// validation.ts:25 — z.string().url() aceita "javascript:alert(1)" (verificado empiricamente)
mediaUrl: z.string().url().max(2000).optional().or(z.literal("")).optional(),
// ContentDetail.tsx:889 — href recebe a URL sem restrição de esquema
Ver mídia
```

## Impacto
Comprometimento de conta/sessão de usuário autenticado ou de administrador da instância.

## Sugestão de correção
Trocar `z.string().url()` por `z.string().refine(u => /^https:\/\//.test(u))` nos schemas de mediaUrl/logoUrl/avatarUrl (validation.ts, auth.ts, settings.ts) e adicionar CSP `script-src 'self'` no helmet.

## Critérios de aceite
- [ ] POST /api/contents/:id/versions com mediaUrl="javascript:alert(1)" retorna 400
- [ ] Conteúdo existente com mediaUrl javascript: renderiza link inerte/bloqueado
- [ ] Teste unitário cobrindo schemes não-https rejeitados
- [ ] helmet CSP ativo em produção

--- ISSUE 4 ---
**[Segurança] validateEnv não rejeita valores placeholder/default de segredo**

Labels: `security, baixa`

## Descrição do problema
A validação de startup checa presença, não valor. SEED_ADMIN_PASSWORD="CHANGE_ME_SEED_ADMIN_PASSWORD" (o placeholder do .env.example) passa direto e vira a senha de admin se ninguém sobrescrever — exatamente o padrão "default público que vira segredo real". ## Evidência
`backend/src/lib/env.ts:68-85`

```
if (!process.env.DATABASE_URL) missing.push("DATABASE_URL");
if (env.CORS_ORIGIN === "*") throw new Error("CORS_ORIGIN must not be wildcard");
// única validação: presença de DATABASE_URL e CORS não-curinga
```

## Impacto
Injeção limitada / risco de configuração insegura silenciosa.

## Sugestão de correção
Em validateEnv(), quando NODE_ENV=production, rejeitar valores da deny-list (CHANGE_ME, exemplo, password123…) para SEED_ADMIN_PASSWORD e segredos de webhook.

## Critérios de aceite
- [ ] NODE_ENV=production + SEED_ADMIN_PASSWORD=CHANGE_ME_SEED_ADMIN_PASSWORD aborta o startup
